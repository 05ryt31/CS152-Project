# Migration prompt template v1

Status: draft (Issue #14). Frozen once both authors sign off; any later change is `v2` and a new `run_id`.

This file is read by the pipeline. The pipeline fills every `{{placeholder}}`, sends **System** and **User**
as two chat messages, and applies the extraction rule to the reply. The same filled template is the input side
of every finetuning example (see `pipeline/MODEL.md`, section 2), so training and evaluation share one prompt.

## Decoding (held constant)

| Setting | Value |
|---|---|
| temperature | 0 (greedy) |
| max_new_tokens | 2048 |
| seed | 0 |
| stop | end-of-turn token only |
| prompt_hash | sha256 of this file, recorded in every output's sidecar JSON |

## System

```
You are an expert programmer who translates programs between programming languages.
You write code that a fluent {{target_language}} programmer would consider natural and idiomatic for that
language's paradigm, not a line-by-line transliteration of the source.
Reply with exactly one fenced code block containing the complete {{target_language}} program and nothing else:
no explanation before or after the block.
```

## User

````
Translate the following {{source_language}} program into {{target_language}}.

The program reads its input from standard input and writes its result to standard output. The translation
must produce byte-for-byte the same standard output as the source program for every input, and exit with
status 0 on success.

Requirements for the {{target_language}} program:
{{target_rules}}

Source program ({{source_language}}, file `{{source_filename}}`):

```{{source_fence}}
{{source_code}}
```

Reply with one fenced code block tagged `{{target_fence}}` containing the complete {{target_language}} program.
````

## Target rules

The pipeline inserts the block for `{{target_language}}` as `{{target_rules}}`. Each block states only what
the harness needs to compile and run the file. It never describes *how* to write the paradigm: idiomaticity is
what we measure, so the prompt must not coach it (the one sentence in the System prompt is the same for every
target and is the only nudge).

### Python

```
- Target runtime: Python 3.14, run as `python {{target_filename}}`.
- Standard library only. No third-party packages.
- Read from `sys.stdin` or `input()`; write with `print`.
```

### JavaScript

```
- Target runtime: Node.js 26, run as `node {{target_filename}}`. ES module syntax is accepted.
- Built-in modules only (`node:fs`, `node:readline`, …). No npm packages.
- Read all of standard input, for example `fs.readFileSync(0, "utf8")`; write with `console.log` or
  `process.stdout.write`.
```

### Java

```
- Target runtime: JDK 25, compiled with `javac` and run as `java {{java_package}}.{{java_class}}`.
- The file must begin with `package {{java_package}};` and declare exactly one top-level
  `public class {{java_class}}` with a `public static void main(String[] args)` method.
- Standard library only (`java.util`, `java.io`, …). No external jars.
- Read standard input with `java.util.Scanner` or `BufferedReader`; write with `System.out`.
```

### Scheme

```
- Target runtime: CHICKEN Scheme 5.3, run as `csi -script {{target_filename}}`.
- Begin the file with `(import scheme (chicken base) (chicken io))`; add other `(chicken …)` modules if needed.
  No eggs (external libraries).
- Read standard input with `read-line` / `read-string` from `(chicken io)`; write with `display`, `write`
  and `newline`.
```

### Haskell

```
- Target runtime: GHC 9.14, run as `runghc {{target_filename}}`.
- Define `main :: IO ()`. Only packages bundled with GHC (`base`, `containers`, `text`, …); no Hackage
  packages that need installing.
- Read standard input with `getContents` / `getLine`; write with `putStr` / `putStrLn` / `print`.
```

### Prolog

```
- Target runtime: SWI-Prolog 10, run as `swipl -s {{target_filename}} -g {{prolog_entry}} -t halt`.
- Define a predicate `{{prolog_entry}}/0` as the program entry point. It must succeed (not fail or throw)
  after writing the output; `halt` is called by the runner.
- Standard SWI-Prolog libraries only (`library(lists)`, `library(readutil)`, …). No packs.
- Read standard input with `read_line_to_string/2` or `read_term/2` on `current_input`; write with
  `format/2`, `write/1` and `nl/0`.
```

## Extraction rule

1. Take the **first** fenced code block in the reply whose tag equals `{{target_fence}}`
   (case-insensitive; `js` and `javascript`, `hs` and `haskell`, `scm` and `scheme`, `pl` and `prolog`,
   `py` and `python` are each treated as the same tag).
2. If no block carries that tag, take the first fenced block of any tag and set `extraction: untagged_fence`
   in the sidecar.
3. If there is no fenced block at all, take the whole reply and set `extraction: no_fence`.
4. Strip nothing else. The harness decides whether it compiles; the pipeline never edits code.

Outputs with `extraction != tagged_fence` are kept in the matrix and counted as a prompt-compliance failure
category in the failure taxonomy (#30).

## Placeholders

| Placeholder | Source | Example |
|---|---|---|
| `{{source_language}}`, `{{target_language}}` | `matrix.json` pair, display names | `Python`, `Haskell` |
| `{{source_fence}}`, `{{target_fence}}` | fixed per language: `python`, `javascript`, `java`, `scheme`, `haskell`, `prolog` | `haskell` |
| `{{source_filename}}` | the source file's basename | `p07_expr_eval.py` |
| `{{source_code}}` | file contents, verbatim | |
| `{{target_filename}}` | `<problem_id>.<ext>` (`py js java scm hs pl`); Java uses `{{java_class}}.java` | `p07_expr_eval.hs` |
| `{{target_rules}}` | the Target rules block for `{{target_language}}` | |
| `{{java_package}}` | `harness` + the output folder path with `/` → `.` (what `run_harness.sh` computes) | `harness.results.raw.run01.p07_expr_eval` |
| `{{java_class}}` | `<ProblemId>` in UpperCamelCase | `P07ExprEval` |
| `{{prolog_entry}}` | `<problem_id>` (the file stem; `run_harness.sh` passes it to `-g`) | `p07_expr_eval` |

## Sign-off notes (#14, Oct 17)

- The one idiomaticity sentence in System stays; it is identical for every target so it cannot bias a pair.
- JavaScript: the harness image (`node:26.10`) auto-detects ES modules in `.js`, so the rule allows ESM.
- Java: the harness derives the class to run from the file's folder path, so `{{java_package}}` is the output
  folder path relative to the project root with `/` as `.`; the pipeline computes it the same way.
- Scheme: the harness runs CHICKEN 5.3 (6.0 is too new for Ubuntu's package manager and likely too new for the
  model's training data), so the rule names 5.3 and nothing CHICKEN-6-specific.
